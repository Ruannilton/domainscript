# TASK-M4.2: Staging na memory UoW: `rolledback` prova reversão real (§22.2)

## 1. Contexto & Objetivo
> **Instrução para o Claude Code:** Leia `design.md` §4.5 (parágrafo "Staging", incluindo o ⚠️ sobre `Sequence`) antes de iniciar. Modifique **apenas** os arquivos de `target_files`.

`memoryTx.Append` grava **direto** em `store.Append`; `memoryUnitOfWork.Run`
apenas devolve o erro de `fn`. O próprio tipo documenta: "commit e rollback são
no-op… eventos já são duráveis no ato de Append". Por isso `then { … rolledback }`
(§22.2) hoje só afirma `err != nil` — não prova que nada foi escrito.

Esta é a única task do ciclo que toca o **runtime vendorizado**. NFR-32 vale
integralmente: `rtsrc/` é stdlib pura, nenhuma dependência nova, nenhum import
de `database/sql`. O adapter `sqlrt` **não** é tocado — ele já é transacional de
verdade.

## 2. Passos de Implementação
- [ ] **Step 1:** `memoryTx.Append` passa a acumular num buffer por
  `aggregateID`, em ordem, em vez de chamar `store.Append`.
- [ ] **Step 2:** `memoryUnitOfWork.Run` aplica o buffer à store **só** quando
  `fn` devolve `nil`; num erro, descarta e a store fica intacta.
- [ ] **Step 3:** `memoryTx.Load` concatena o que está na store com o buffer
  daquele stream, na ordem — **read-your-writes** dentro do mesmo `Run`
  (REQ-59.2), a mesma semântica que o adapter SQL já tem.
- [ ] **Step 4:** ⚠️ **`Sequence`:** hoje `EventStore.Append` carimba `Sequence` a
  partir do tamanho do stream persistido. Com staging o carimbo acontece no
  **flush** — garantir que dois `Append` ao mesmo stream no mesmo `Run` produzam
  sequências **contíguas**, e que o `Load` intra-`Run` enxergue metadados
  coerentes. Este é o ponto de maior risco da task; validá-lo explicitamente.
- [ ] **Step 5:** Preservar a publicação pós-commit: os eventos continuam
  entregues a `Publisher.Publish` na ordem de append, só depois de `fn` retornar
  `nil` — e uma falha de publicação continua sendo logada, nunca devolvida (a
  transação já commitou).
- [ ] **Step 6:** Em `codegen/gentest.go`, fazer `rolledback` afirmar que a store
  ficou **intacta** (não só `err != nil`) — capturar o estado antes do `Run` e
  comparar depois.

## 3. Testes & Validação

### Casos de Teste do Runtime (rtsrc_test.go)
- [ ] **TEST-1 (positivo):** um `Run` que devolve `nil` deixa os eventos na store,
  com `Sequence` contíguo — incluindo o caso de **dois `Append` ao mesmo stream**
  no mesmo `Run` (Step 4).
- [ ] **TEST-2 (negativo):** um `Run` que devolve erro **não** deixa evento algum
  na store, e nada é publicado.
- [ ] **TEST-3 (read-your-writes):** um `Tx.Load` posterior a um `Tx.Append` no
  mesmo `Run` enxerga os eventos staged, na ordem, concatenados aos já
  persistidos.
- [ ] **TEST-4 (guarda comportamental):** os testes existentes de
  `memoryUnitOfWork`/`MemoryEventStore` seguem verdes — commit continua durável,
  publicação pós-commit inalterada.

### Casos de Teste de gentest
- [ ] **TEST-5 (par NFR-4):** um cenário `then { … rolledback }` cujo `Run` falha
  → o teste gerado **passa** (store intacta); um cenário que declara `rolledback`
  mas cujo `Run` **sucede** → o teste gerado **falha** com mensagem clara.
- [ ] **TEST-6 (byte-identidade, NFR-31):** `wallet` e `shop` — incluindo seus
  `*.test.ds` — geram Go byte-idêntico salvo pela nova asserção de `rolledback`.
