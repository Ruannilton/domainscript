# TASK-M1.3: `list <Aggregate>` com cláusulas (where/orderBy/skip/take/as)

## 1. Contexto & Objetivo
> **Instrução para o Claude Code:** Leia `design.md` §4.2 (a tabela de comparação com `hoistLoadCollection`) e §5.1 antes de iniciar. Modifique **apenas** os arquivos de `target_files`.

M1.2 entregou a forma base. Esta task fecha a forma real que o `pizzeria` usa:

```
return list KitchenTicket t
       where t.status in [TicketStatus.Pending, TicketStatus.Preparing]
       orderBy t.createdAt ascending
       as KitchenTicketVW
```

**A máquina de cláusulas já existe e NÃO deve ser reimplementada.**
`hoistLoadCollection` (`lower/stmt.go`, Marco I) já faz exatamente três passos —
carregar a fonte, montar o `Query[T]` via
`hoistQueryPredicate`/`hoistOrderBy`/`hoistSkipTakeExpr`, e chamar
`runtime.SelectSlice`. Só o **passo 1** (a fonte) difere aqui: em vez de uma
instância e seu campo `AppendList`, a fonte é a coleção enumerada de M1.2. Os
passos 2 e 3 são reusados **sem alteração**.

## 2. Passos de Implementação
- [ ] **Step 1:** Em `lower/stmt.go`, criar `hoistListAggregate`, espelhando
  `hoistLoadCollection`: passo 1 emite a materialização de M1.2 (enumerar +
  `Load<Agg>` por id + acumular `[]<aggState>`); passos 2 e 3 **chamam as mesmas
  funções** que `hoistLoadCollection` chama, sem cópia de lógica.
- [ ] **Step 2:** Rotear a partir de `decl_query.go`: quando
  `tryEmitListAggregate` vê **cláusulas presentes**, delegar ao caminho hoisted,
  no mesmo espírito com que `tryEmitListVO` reescreve para `load Agg(p).<campo>
  […]` e delega a `emitHoistedQueryReturn`.
- [ ] **Step 3:** `as <View>` continua tratado **fora** do hoisting — remover a
  cláusula `as` antes de hoistear (senão `TypeEnv` inferiria `List<V>` para uma
  variável Go que recebe `[]T`) e aplicar `emitAsProjection` por cima, exatamente
  como `emitHoistedQueryReturn` já documenta.
- [ ] **Step 4:** Garantir que o binding (`t`) resolve ao struct de state no
  predicado e no `orderBy` — o `ItemTypeOf` ajustado em M1.2 é o que sustenta
  isso; `hoistQueryPredicate` não precisa saber que a fonte mudou.
- [ ] **Step 5:** Confirmar que `ensureListClausesWellFormed` (ou equivalente) é
  aplicado a esta forma, para uma cláusula malformada dar o **mesmo** erro claro
  que já dá nas outras formas de `list`.

## 3. Testes & Validação

### Casos de Teste Unitários / Golden Tests
- [ ] **TEST-1 (positivo):** fixture com `list <Aggregate>` usando `where` +
  `orderBy` + `as View` → gera e `gentest.SmokeCompile` **builda**; e um teste
  comportamental sobre o projeto gerado prova que o filtro e a ordenação
  realmente se aplicam (não só que compila).
- [ ] **TEST-2 (positivo, paginação):** a mesma forma com `skip`/`take` devolve a
  janela correta.
- [ ] **TEST-3 (negativo):** cláusula malformada (ex. `orderBy` sobre campo
  inexistente no state) produz erro de geração claro, no mesmo formato das
  outras formas de `list`.
- [ ] **TEST-4 (byte-identidade, NFR-31):** `list <VO> [cláusulas]` e
  `load X(id).<campo> [cláusulas]` — as duas formas que compartilham a máquina
  de cláusulas — geram Go **byte-idêntico** ao de hoje. Esta é a guarda central
  da task: a extração não pode ter mudado o caminho existente.
- [ ] **TEST-5 (determinismo):** gerar duas vezes produz bytes idênticos, e a
  Query **sem** `orderBy` devolve a ordem estável de `ListStreams` (M1.1).
